# Nakshatra

Sinhala, Tamil and English astrology and almanac app for Sri Lanka — daily horoscope, nekath (auspicious timings), rahu kalaya, panchanga, birth charts and porondam compatibility.

All astronomical calculations run **on-device**. No birth data is uploaded to any server.

> For entertainment purposes only.

## Configuration

The following files are **not** in version control and must be supplied locally.
Nothing in this list should ever be committed.

| File | Purpose |
| --- | --- |
| `android/key.properties` | Release signing credentials |
| `android/upload-keystore.jks` | Upload key |
| `android/app/google-services.json` | Firebase Android config (not yet used) |
| `lib/firebase_options.dart` | Generated by FlutterFire CLI (not yet used) |
| `env/dev.json`, `env/prod.json` | Build-time config — copy `env/example.json` |

`android/local.properties` is generated by Flutter and is also ignored.

### Build-time configuration

Values are passed with Flutter's built-in `--dart-define-from-file` and read
through `lib/core/config/env.dart`. The launch configs already do this; from the
command line:

```bash
flutter run --flavor dev --target lib/main_dev.dart --dart-define-from-file=env/dev.json
```

**Nothing in `env/*.json` is a secret.** Every value is compiled into the APK
and can be extracted from it — AdMob identifiers appear in the Android manifest
regardless, and a RevenueCat *public* SDK key is published by design. They live
outside version control so dev and prod can differ and so identifiers rotate
without a commit, not because they are confidential.

`env/dev.json` ships with Google's official AdMob **test** identifiers. Never
put live ad units in a debug build: clicking your own live ads is the fastest
route to a permanent AdMob ban.

Real secrets never reach the app. The keystore and its passwords stay in
`android/key.properties` locally, and in GitHub Actions secrets for CI.

### CI secrets

`.github/workflows/release.yml` builds a signed bundle. It runs only on tags and
manual dispatch, never on pull requests — this repository is public, and a
workflow holding signing secrets must not check out untrusted code.

Repository **secrets** (Settings → Secrets and variables → Actions → Secrets):

| Name | Value |
| --- | --- |
| `KEYSTORE_BASE64` | `base64 -w0 android/upload-keystore.jks` |
| `KEYSTORE_PASSWORD` | `storePassword` from `key.properties` |
| `KEY_PASSWORD` | `keyPassword` from `key.properties` |
| `KEY_ALIAS` | `upload` |

Repository **variables** (same page, Variables tab) — not secrets, so they are
visible in logs, which is fine:

`ADMOB_APP_ID`, `ADMOB_BANNER_UNIT_ID`, `ADMOB_INTERSTITIAL_UNIT_ID`,
`ADMOB_REWARDED_UNIT_ID`, `REVENUECAT_PUBLIC_SDK_KEY`

None of these are needed until AdMob lands; the release workflow builds fine
with them empty.

## Releasing

`.github/workflows/release.yml` builds, signs, and optionally publishes to Play.
Trigger it from **Actions -> Release -> Run workflow**, choosing a track, or by
pushing a `v*` tag.

### versionCode is automatic

Play permanently rejects a duplicate `versionCode`, so it is never hand-edited.
CI derives it from the workflow run number:

```
versionCode = github.run_number + VERSION_CODE_OFFSET   (offset 100)
```

Run numbers only increase, so codes only increase. The offset clears codes
already burned by manual uploads — run 1 becomes 101. **Never lower the offset**;
that regenerates codes Play has already seen and will refuse. `versionName`
still comes from `pubspec.yaml`, so bump that by hand for a real version change.

### Publishing to Play automatically

Uploading needs a Google Play service account. One-time setup:

1. **Play Console -> Setup -> API access -> Create new service account**, which
   sends you to Google Cloud.
2. In Google Cloud: create a service account, then **Keys -> Add key -> JSON**
   and download it.
3. Back in Play Console, grant that account access to this app with the
   **Release manager** role (or at minimum: release to testing tracks).
4. Add the JSON file's entire contents as the repository secret
   `PLAY_SERVICE_ACCOUNT_JSON`.

Until that secret exists the workflow still builds and signs, and attaches the
bundle as an artifact for manual upload — it just skips publishing. The
`dry_run` input forces that behaviour deliberately.

> Google requires at least one bundle uploaded manually through the console
> before the API will accept uploads for an app. Do the first internal release
> by hand; automation works from the second onwards.

That service account JSON is the most dangerous credential in this project — it
can publish to production. Treat it like the keystore.

## Release signing

Release builds read credentials from `android/key.properties` (git-ignored).
Without it the build still succeeds but is signed with **debug** keys and
Play will reject it — see `android/key.properties.example`.

To create your upload key:

```bash
keytool -genkey -v -keystore android/upload-keystore.jks -storetype JKS -keyalg RSA -keysize 2048 -validity 10000 -alias upload
```

Then copy `android/key.properties.example` to `android/key.properties` and fill
in the passwords you chose.

> Enable **Play App Signing** on the first upload. Google then holds the app
> signing key and this keystore is only the *upload* key, which Google can
> reset if it is ever lost. Without it, losing this file means the app can
> never be updated again.

Back the keystore up somewhere outside this machine.
